# 20 — iCHEF 徹底拆解 × 我們的 POS 複刻藍圖

> 目的：把 iCHEF（台灣 15,000+ 店、月費 $1,950 起的 iPad POS）拆到骨頭，
> 對照我們既有的 `restaurant_api`（25 表 FastAPI 後端），畫出「前台 + 後台 + 平板點餐」的複刻路線。
> 撰寫日期：2026-07-09。來源：iCHEF 官網/知識庫/部落格 + 第三方比較文（清單見文末）。

---

## 0. TL;DR

- iCHEF 本質 = **iPad 原生 App（前台）+ 雲端後台（管理/報表）+ 「雲端餐廳」消費者網頁（掃碼點餐/訂位/外帶）+ 出單機網路**，靠月費 + 金流抽成 + 模組加購賺錢。
- 我們的後端地基比想像厚（33 表、12 router：庫存、成本、HR、會員儲值集點、訂位候位、KDS API 都在），**缺的是三塊**：① 桌位模型 + POS 型訂單操作（現在的 orders 是「接外部 POS 單」的帳本，不能開桌加點）② 全部前端（POS/桌邊平板/KDS/後台，repo 一行前端框架都沒有）③ WebSocket 即時同步層。
- 複刻策略不是抄 iPad App，而是走 **Web-based PWA**：任何平板（Android/iPad/便宜陸板）開瀏覽器就是 POS；桌邊平板 = 同一套前端的「顧客模式」。一套程式碼、兩種角色、WebSocket 即時同步。
- iCHEF 的結構性弱點（多店即時整合弱、生態封閉、iPad-only、無螢幕 KDS）正好是我們的差異化空間。

## 1. iCHEF 是什麼（商業定位）

| 面向 | 事實 |
|---|---|
| 成立 | 2012（麻膳堂團隊出身，「餐廳老闆做給餐廳的系統」） |
| 規模 | 台灣 15,000+ 間餐廳使用，市佔第一梯隊 |
| 型態 | iPad 原生 POS App + 雲端後台 SaaS |
| 定價 | 月費制：$0 輕量方案 / $1,950 標準 / $2,950 進階 / $3,950 頂級 — 功能大致相同，差在**會員數量、庫存品項數、外送接單量等用量上限** |
| 額外收費 | 線上點餐金流抽成 **2.2% 起**；總部系統每店 **$1,000/月**；硬體（出單機、錢箱、讀卡機）另購 |
| 客群 | 中小型獨立餐廳為主（小吃、咖啡廳、簡餐、飲料店） |

**商業模式的三層漏斗**：低月費把 POS 塞進店裡 → 掃碼點餐/線上外帶把金流導進自家通道抽 2.2% → 會員/總部/外送整合模組做增購。POS 是入口，金流與資料才是本體。

### 1.5 iCHEF 到底解決什麼問題（複刻時對著痛點做，不是對著功能抄）

| # | 餐廳痛點 | iCHEF 的解法 | 我們複刻時要贏在哪 |
|---|---|---|---|
| 1 | 外場人力貴、缺工 | 掃碼點餐讓客人自己點，服務生免開桌免送單 | 桌邊平板 + 手機 QR 雙軌，Android 便宜平板壓硬體成本 |
| 2 | 手抄單點錯、漏單 | 點餐直接分流到廚房出單機，零轉抄 | 螢幕 KDS + 出餐回報，狀態閉環到桌況 |
| 3 | 尖峰結帳塞車 | 多台 iPad 同步、行動支付相機掃碼 | Web POS 任何裝置都是收銀台，開機成本近零 |
| 4 | 外送平台各一台平板、單子亂 | UberEats/foodpanda 進同一台 POS 出單 | 同樣做整合，且外送單一樣扣 BOM（我們已有） |
| 5 | 老闆不在店，營運黑箱 | 雲端報表手機看、跟前期自動比對 | 我們單庫多租戶 → 多店「即時」看板（iCHEF 弱項） |
| 6 | 食材成本失控、被偷料看不出來 | BOM 自動扣 + 移動平均成本 + 消耗查詢 | 已有，再加 `cogs_variance` AI 異常偵測（超車點） |
| 7 | 客人來一次就不回頭 | 手機號自動入會、零秒集點、分眾推播 | 已有更深：儲值、RFM、裂變、輪盤（超車點） |
| 8 | 電子發票申辦麻煩 | 內建開立（財政部核可加值中心），全通路一致 | 欄位已齊，串加值中心即可 |
| 9 | 訂位 no-show 賠掉整桌 | 訂位訂金預付、結帳自動抵扣 | 訂位 API 已有，補金流即可 |
| 10 | 員工刪單、亂給折扣、偷開錢箱 | 權限密碼 + 全操作記錄 | audit_log append-only 已就位，比它更不可竄改 |

一句話：**iCHEF 賣的不是點餐機，是「少請一個人、少漏一筆錢、多留一個客」**。我們每個 Phase 的驗收都應該回答「這一步替店家省了哪個人/錢/客」。

## 2. 系統總架構拆解

```
┌─────────────────────────── 消費者端（Web，免安裝）────────────────────────────┐
│  掃碼點餐頁（桌位QR/訂單QR） · 線上外帶頁（AI點餐員） · 線上訂位頁（訂金金流）│
│  Google Maps 訂位入口 · LINE 官方帳號入口                                      │
└──────────────────────────────────┬───────────────────────────────────────────┘
                                   │ HTTPS
┌──────────────────────────────────▼───────────────────────────────────────────┐
│                        iCHEF 雲端（後台 + 同步中樞）                          │
│  菜單/商品/口味 · 會員CRM · 庫存BOM · 報表 · 電子發票(財政部字軌) · 權限稽核  │
│  外送平台串接(UberEats/foodpanda) · 支付串接(LINE Pay/街口/台新A910·A920)     │
│  總部系統（跨店菜單/報表/會員圈）                                             │
└──────────────────────────────────┬───────────────────────────────────────────┘
                                   │ 即時同步（雙向）
┌──────────────────────────────────▼───────────────────────────────────────────┐
│                      店內（iPad 原生 App + 出單機網路）                        │
│  多台 iPad 同步操作（點餐/結帳/桌況） · 離線模式（斷網可點餐結帳，回網補傳）  │
│  7 天內須連網做一次安全驗證 · 出單機依「印單規則」分流到各工作站（廚房/吧台） │
└───────────────────────────────────────────────────────────────────────────────┘
```

架構上的四個關鍵決定（值得學）：

1. **前台放 iPad 原生 App、資料主權在雲端**：店內斷網照常營業（離線佇列，回網自動補傳），但強制 7 天內連網驗證一次，避免資料失聯。
2. **多 iPad = 同一店的對等節點**：任何一台都能點餐/結帳/看桌況，即時互相同步 — 這是「前台能連線平板」的本質。
3. **消費者端全部走 Web**（掃碼點餐/訂位/外帶都是網頁），免安裝、免上架，用 QR code 當入口。
4. **廚房不用螢幕 KDS、用出單機**：熱感印表機 + 「印單規則」把品項分流到工作站。便宜、耐操、不用教學 — 但也是它的天花板（無法回報出餐狀態）。

## 3. 模組逐一拆解

### 3.1 前台 POS 點餐（iPad App 核心）

- 內用開桌 / 外帶 / 快速結帳三種單流；桌邊點餐、結帳、熟客招呼多台 iPad 同步操作。
- 商品結構：分類 → 商品 → **口味/加料（modifier groups）**，可設必選/多選/加價。
- 訂單操作：併桌、拆單、轉桌、部分結帳（AA）、暫結、招待、退菜（留稽核記錄）。
- 折扣引擎:單品折扣 / 整單折扣 / 折讓，全部進操作記錄。
- 敏感操作（刪單、折扣、開錢箱）可設**權限密碼**，留操作人記錄。

### 3.2 桌位管理

- 平面桌位圖，每桌即時狀態：空桌 / 入座 / 備餐中 / 出餐完成 / **下一組訂位時間**。
- 與訂位系統聯動：依預定時間、人數、可訂桌位**自動安排訂位桌位**。
- 桌況即為訂單狀態的投影 — 桌位卡片上直接看到已點金額與時間。

### 3.3 內用掃碼點餐（= 顧客自助點餐）

兩種 QR 模式（設計得很聰明，值得照抄）：

| 模式 | 運作 | 適用 |
|---|---|---|
| **桌位 QR**（固定桌卡） | QR 永久綁定桌號；掃了直接點餐，可設定「先結帳才成單」；服務生免開桌免送單 | 快餐、自助型 |
| **訂單 QR**（動態單據） | 店員開桌後由出單機印出該單專屬 QR，客人掃碼**加點**；訂單結案 QR 自動失效 | 正餐、桌邊服務型 |

- 加點 QR 可**限定菜單子集**（只開放副餐/飲料/服務鈴品項）→ 客人加點不用舉手。
- 客人送單後，POS 端**推播 + 音效**提醒新單進來。
- 每次點餐用**手機號碼**登入 → 自動變會員（點餐即獲客）。
- 效果主張:省外場人力、拉高客單價（AI 推薦加購）。

### 3.4 線上訂位 / 候位

- 消費者自助訂位網頁 + 現場候位管理 + 訂位提醒。
- **訂位預付款**：可設「大桌收訂金」「依人數收訂金」「訂金與餐費取高」等規則；線上刷卡收款；結帳時 POS 自動抵扣預付款。
- **Google 訂位入口**：綁 Google 商家檔案後，消費者從 Google Maps / 搜尋直接訂位（審核 1–3 天）。
- 訂位 → 桌位 → 備料 → 金流 四件事在同一系統裡閉環（這是它 2023 年才補齊、對打 inline 的主張）。

### 3.5 線上點餐（外帶/外送自有通道，「雲端餐廳」)

- 店家專屬線上點餐網站（免上架費），內建「**AI 點餐員**」做加購推薦。
- 金流 2.2% 起（信用卡/LINE Pay），這是 iCHEF 的抽成引擎。
- 訂單直接進 POS 與出單機，不用另一台平板。

### 3.6 外送平台整合（UberEats / foodpanda）

- 業界第一家雙平台串接：**免外送平台平板、免手 key**，訂單自動進 POS。
- 在 iCHEF 後台直接維護外送平台專屬菜單（價格可不同），一鍵同步。
- 外送單一樣走工作站出單、納入銷售分析、**自動扣 BOM 庫存**。

### 3.7 廚房出單（工作站分單）

- 每台出單機可設多條「**印單規則**」：哪些商品、什麼時機、什麼版面。
- 工作站命名（廚房/吧台/甜點站），單品自動分流；廚房單字體加大。
- 總部可設**跨店出單規則**。
- 注意：iCHEF 是「印表機 KDS」，沒有螢幕型 KDS、沒有出餐回報 → 桌況的「備餐中/出餐完成」靠人工按。

### 3.8 結帳與支付

- 現金（錢箱聯動 mPOP）、信用卡（台新 A910/A920 讀卡機：感應/插卡/Apple Pay/Google Pay）、LINE Pay、街口、悠遊付、全盈+PAY。
- 行動支付用 **iPad 相機直接掃**客人付款條碼，免外接掃描槍。
- 多元支付方式全部記進報表分帳。

### 3.9 電子發票

- iCHEF 是**財政部核可的加值服務中心**，發票功能內建不加價。
- 支援：字軌匯入、統編、載具（手機條碼/自然人憑證）、捐贈碼、作廢/折讓。
- 掃碼點餐/線上外帶/外送單也能開發票 — 全通路發票一致。

### 3.10 會員 CRM（全通路會員）

- 「**零秒集點**」：結帳單據上印集點 QR，客人自己掃、POS 自動核發點數 — 店員零操作。
- 內用/外帶/外送/掃碼點餐全通路集點；手機號碼 = 會員主鍵。
- 儲值金、點數兌換規則自訂、可全自動。
- 標籤系統：同生日自動貼標、同餐點喜好自動分類 → 後台勾條件發**分眾訊息**（獨家整合簡訊 + LINE 官方帳號）。
- 總部「會員模組」：跨分店共享會員、點數互通，建品牌會員圈。

### 3.11 庫存與成本

- 自訂分類/品項/單位、安全庫存警示。
- **BOM 自動扣**：每道餐點連結多種食材與每份消耗量，賣一份自動扣。
- **移動平均成本**：依進貨數量與單價自動算庫存平均進價。
- 後台可查任意期間每種食材消耗量;盤點有記錄。

### 3.12 報表分析（雲端後台）

- 「懶人報表」：自動跟前期比對；營業分析、銷售排行、品項/口味/來客/折扣/時段分析、商品銷售分布圖。
- 手機就能看（老闆不在店也能管）。
- 操作稽核：刪單、折扣、開錢箱全記錄。

### 3.13 總部系統（多店，$1,000/店/月）

- 邀請制掛分店；跨店菜單管理（總部設定、分店套用、保留分店微調彈性）。
- 跨店報表（可自訂「營業日切點」）、跨店會員圈、跨店出單規則。
- 第三方評測普遍指出：**多店「即時」整合是它的弱項** — 跨店數據非即時，總部看板要事後彙整。

## 4. iCHEF 的結構性弱點（= 我們的機會）

| 弱點 | 細節 | 我們的打法 |
|---|---|---|
| iPad-only | 硬體綁蘋果，一台 iPad 上萬；Android 便宜平板不能用 | Web PWA：任何平板/舊手機/電腦都是 POS |
| 生態封閉 | 僅能用自家模組，第三方串接受限、無公開 API 生態 | API-first（我們本來就是 FastAPI），一切皆可串 |
| 多店即時性 | 總部報表非即時、跨店整合要人工 | 單一 PG 多租戶（`tenant_id` 天生就在），總部即時看板是免費副產品 |
| 印表機 KDS | 無螢幕 KDS、無出餐狀態回報，桌況靠人工按 | 螢幕 KDS（平板再利用）：出餐回報自動改桌況 |
| 金流抽成 | 線上單 2.2% 起、綁自家金流 | 自選金流（Line Pay/TapPay/藍新），抽成是選項不是綁架 |
| AI 只做加購 | 「AI 點餐員」只在推薦加購 | 我們的 LLM 縱深：對帳異常、成本異常偵測（cogs_variance）、營運日報 |

## 5. 對照我們的 `restaurant_api`：已有 vs 缺（2026-07-09 實地盤點）

> 實況比文件記載更好：目前是 **33 張表、12 個 router**，後場（庫存/成本/HR/會員/行銷）在 API 層大致蓋完。
> 但 `orders` 是「**接收外部 POS 單**」的設計（`external_pos_id`/`pos_source` 進單、不能加點編輯、沒有桌號欄位）—
> 要「自己就是 POS」，核心工作是把訂單模型從『帳本』升級成『活訂單』+ 蓋出整個介面層。

### 5.1 已有（對應 iCHEF 模組）

| iCHEF 模組 | 我們已有 | 狀態 |
|---|---|---|
| 訂單核心 | `orders` router：冪等進單、查單（含明細/折扣/付款）、關單、作廢（自動回沖庫存） | 🟡 進單型，缺開桌/加點/改單 |
| 廚房出單 | `kitchen` router：KDS 看板輪詢 + 品項狀態機（cook/ready/serve/cancel），`order_lines` 已有 6 個 KDS 欄位 | ✅ API 齊，缺螢幕前端 + 推播 |
| 訂位/候位 | `reservations` + `walk_in_queue` router：訂位狀態機（confirm/seat/no_show）、現場排隊叫號 | ✅ API 齊，缺訂金金流 + 消費者頁 |
| 庫存/BOM | `stock` router（進貨/盤點/ledger）、`recipes` BOM 表、stock_movements append-only | ✅ |
| 成本事件 | `events` router（報廢/員工餐/試吃）、`cogs_variance` job | ✅ |
| 員工/HR | `clock` router（打卡/請假/勞基工時桶）、shifts、public_holidays | ✅ |
| 會員 CRM | `customers` router：會員 CRUD、集點、**儲值錢包**、推薦裂變；RFM 分眾 + LINE 分眾推播 | ✅ 比 iCHEF 基本盤還深 |
| 行銷 | `campaigns` 輪盤抽獎引擎（17 端點）、`ugc` 打卡審核、`membership` 成長分析 | ✅（iCHEF 沒有的東西） |
| 稽核 | audit_log append-only + `audit_service`、cash_drawer_sessions | ✅ |
| 發票 | orders 上已有完整發票欄位（字軌/載具/統編/作廢折讓，照財政部生命週期建 enum） | 🟡 欄位齊，**未串加值中心**（只記錄不上傳） |
| 支付 | order_payments（多付款方式 + fee_amount） | 🟡 只記錄，未串金流 |
| LINE | `line_webhook` router（驗簽）+ LineMessenger 抽象（Stub 完成） | 🟡 HTTP 實作待補 |
| 多租戶/總部 | 所有業務表 `tenant_id`，單庫多店 | ✅ 天生比 iCHEF 總部即時 |

### 5.2 缺的（= 這次要蓋的）

1. **桌位/樓面模型**：全 repo 沒有任何 tables/seats 實體；`Order` 連 `table_number`、`order_type`（內用/外帶/外送）欄位都沒有 → 新表 + orders 加欄。
2. **POS 型訂單操作**：開桌、逐項加點/改量/退菜、轉桌併桌拆單 — 現在的 orders 只能整張進單。
3. **菜單 CRUD API**：menu_categories/menu_items 有模型沒有 API（現在只能 seed）。口味/加料 modifier 結構也還沒有。
4. **前端全部**：repo 內沒有任何 package.json；只有輪盤抽獎 demo HTML。POS、桌邊點餐、KDS、管理後台四個介面都要從零蓋。
5. **即時同步層**：WebSocket 事件廣播（新單推播、桌況、KDS 出餐回報）。
6. **認證/權限 router**：employees 有角色欄位但沒有登入與權限 API（iCHEF 的操作密碼/稽核閘門要靠它）。
7. **支付/發票「串接」**：TapPay 或藍新金流、財政部加值中心上傳（欄位都在，只差通道）— 可後 phase。
8. **報表 API**：資料都有（orders/payments/costs），缺彙總報表端點與後台畫面。

## 6. 我們的複刻架構（提案）

### 6.1 總圖

```
        顧客手機(掃桌位QR)      桌邊平板(顧客模式)       店員平板(POS模式)      廚房平板(KDS)
              │                      │                       │                    │
              └──────────────┬───────┴───────────┬───────────┴────────────┬───────┘
                             │   同一套 Web 前端（PWA），依「角色 + 裝置註冊」變身   │
                             │                                                     │
                    ┌────────▼─────────────────────────────────────────────────────▼──┐
                    │                    FastAPI (restaurant_api)                      │
                    │   REST（點餐/結帳/桌位/菜單） + WebSocket hub（訂單事件廣播）    │
                    │   既有:orders/stock/clock/cost/audit  新增:tables/kds/devices   │
                    └────────────────────────────┬──────────────────────────────────────┘
                                                 │
                                        PostgreSQL 16（25+N 表，tenant_id 多店）
```

### 6.2 關鍵設計決定

1. **一套前端、四種角色**：`pos`（店員）/ `table`（桌邊平板，鎖定桌號的 kiosk 模式）/ `kds`（工作站）/ `customer`（手機掃碼）。裝置註冊表（device token + 角色 + 綁定桌號/工作站）控制誰能做什麼 — 桌邊平板只能點自己那桌、不能結帳、不能看報表。
2. **平板 = 訂位點餐一體**：桌邊平板閒置時顯示「本桌狀態/訂位資訊」，入座掃店員卡或輸桌號開單後變點餐模式；客人自己點 → 走 iCHEF「訂單 QR」同款邏輯（限定菜單子集、加點免舉手、送單推播到 POS）。
3. **即時同步用 WebSocket + 事件表**：訂單事件先落 DB（append-only，符合我們 ledger 哲學）再廣播；前端斷線重連用 `last_event_id` 補拉 — 這比 iCHEF 的黑盒同步更可稽核。
4. **離線策略務實版**：Phase 1 不做全離線（iCHEF 花了十年）；做「弱網容忍」— 前端操作佇列 + 冪等 API（client_request_id 去重），斷線 30 秒內無感。全離線列為後期選項。
5. **KDS 用螢幕不用印表機**（先）：平板瀏覽器全螢幕即 KDS；出餐按鈕回寫訂單品項狀態 → 桌況自動變。出單機列印之後補（ESC/POS over LAN 不難）。
6. **金錢照家規**：所有前端金額顯示由後端算好（Decimal），前端永不做金額運算。

### 6.3 資料層改動（草案，動工前先過 docs/04 設計審查）

新表：
- `dining_tables`（桌位:tenant/store、名稱、區域、座位數、桌位QR token）
- `table_sessions`（開桌:桌位 × 訂單 × 狀態機 空桌→入座→備餐→出餐→結帳→清桌）
- `devices`（裝置註冊：角色、綁定桌位/工作站、token、最後心跳）
- `order_events`（append-only 事件流，WebSocket 的真相來源 — 符合家規 ledger 哲學）
- `menu_modifier_groups` + `menu_modifiers`（口味/加料：必選/多選/加價 — iCHEF 3.1 的核心結構）

既有表加欄（不破壞既有進單流程）：
- `orders` + `order_type`（dine_in/takeout/delivery）、`table_session_id`、`channel`（pos/table_qr/online）
- `order_lines` 的 KDS 6 欄位照用（docs/09 F6 已就位）；kitchen_station 的分流規則表視 P3 需要再加

### 6.4 建造順序（提案，各 Phase 完成即可獨立展示）

| Phase | 內容 | 站在什麼既有地基上 |
|---|---|---|
| **P1 店員 POS** | 桌位模型 + 菜單 CRUD API + 訂單升級（開桌/加點/改單）+ POS Web 前台（桌位圖、點餐、現金結帳）+ WebSocket 同步 | orders/kitchen router、audit、cash_drawer_sessions |
| **P2 桌邊點餐** | 同一前端的顧客模式（綁桌 kiosk）+ 桌位 QR 手機版 + 加點限定菜單 + 新單推播到 POS | P1 全部 + devices 表 |
| **P3 KDS 螢幕** | 工作站看板前端 + 出餐回報 → 桌況自動更新（**API 已存在**，主要是前端 + 把輪詢升級成 WebSocket） | `kitchen` router 現成 |
| **P4 會員+折扣** | 手機號會員綁單、集點 QR、discount_resolver 上線、儲值付款進 POS | customers/儲值/集點 router 現成 |
| **P5 金流+發票** | TapPay/藍新、電子發票加值中心上傳（欄位已齊，補通道） | orders 發票欄位、order_payments |
| **P6 訂位+線上** | 訂位訂金金流 + 消費者訂位頁 + 外帶自有通道（**訂位/候位 API 已存在**） | reservations/walk_in_queue router 現成 |

前端技術選型（P1 動工前定案）：傾向 **React + Vite PWA**（或 HTMX 極簡版先驗證流程）；狀態同步走 WebSocket + TanStack Query。這是唯一還沒定的大選型。
